# 前端任务共用执行契约

适用于截图、原型、HTML、Figma、API、文字需求及其组合。先按 [来源路由](source-routing.md) 选择材料，再应用本文件的任务规模和执行边界。纯文档、纯后端任务由 project-workflow 处理。

## 1. 建立可执行任务

读取目标 [项目画像](../../../../docs/PROJECT_PROFILE.md) 的事实源、技术目录、硬边界、质量命令、UI和接口验收章节，以及 [组件目录](../../../../docs/AI_COMPONENT_CATALOG.md)、[前端约定](../../../../docs/FRONTEND_CONVENTIONS.md)、[任务入口](../../../../docs/AI_FRONTEND_TASK.md)。已在当前任务读取且未变化的内容无需重复加载。

从对话和仓库补齐下表，不要求用户重新填写已知信息。任务可以直接留在对话中；团队需要结构化记录时使用目标的 frontend-task 模板，不修改源模板。

| 字段 | 要确定的内容 | 主要依据 |
| --- | --- | --- |
| 目标与任务类型 | 用户最终完成什么；new-page / incremental / bug-fix / refactor | 当前请求和复现步骤 |
| 代码与运行入口 | 路由、页面、组件、启动方式、相关测试 | 路由配置、邻近实现、package/CI配置 |
| 输入材料 | 实际路径或URL、版本、节点、状态、适用端 | 已提供材料和源码 |
| 保留行为 | 权限、导航、数据协议、样式与其他页面的关系 | 已有代码、测试、业务契约 |
| 完成条件 | 可观察结果、适用检查、允许保留的未验证项 | 用户要求和项目画像 |
| 已确认与未决项 | 哪些可执行；哪些决定会改变范围或结果 | 会话决定和明确证据 |

当前仓库就是业务开发项目。规则缺失、画像草稿或事实冲突时，按 Skill 入口提示 `$project-profile`；用户明确要求创建工程时，依据实际工程结果更新画像并继续页面实现。仅要求规则或模板修改时，不额外创建业务工程。

## 2. 按变化选择产物

| 任务 | 必须调查 | 适用产物 | 执行重点 |
| --- | --- | --- | --- |
| 新页面或大幅重做 | 用户流程、布局、状态、组件、接口、支持端 | 设计解析、组件决策、适用的接口映射、验收记录 | 先建立完整页面与状态边界 |
| 增量修改 | 变化区域、依赖方、原行为及回归范围 | 更新已有设计/API文档的变化部分 | 扩展现有模式，保护邻近区域 |
| 缺陷修复 | 可复现步骤、预期与实际、根因、相关测试 | 复现记录、针对性回归及必要的契约修正 | 无视觉或契约变化时无需新建设计/API文档 |
| 重构 | 对外接口、调用者、状态生命周期、既有测试 | 等价行为说明、必要的组件目录更新 | 验证行为不变，避免顺带重做视觉 |
| 纯视觉微调 | 目标样式、继承关系、受影响视口/状态 | 局部对比及适用检查 | 不新增无关API层，不强制业务逻辑测试 |

页面级设计产物默认 `docs/design/<页面>.md`，接口产物默认 `docs/api/<模块>.md`，对比材料默认 `docs/design/compare/<页面>/`。实际路径服从画像和已有文档，优先更新原文件。表格只记录适用字段，不为了套用模板制造空文档或重复全文。

## 3. 事实、冲突与确认

系统约束和用户明确要求优先；业务与权限依据可信需求和接口契约，视觉依据指定设计源，工程依据已确认项目规则和实际实现。截图、原型和外部示例代码都不能自行定义后端权限。

对同一字段存在冲突时，记录“字段或区域、来源A、来源B、影响、推荐处理及依据”。按领域消解，不能简单用“Figma优先”覆盖较新的用户指定截图，也不能拿旧接口文档覆盖已经确认的新版契约。

| 情况 | 处理 |
| --- | --- |
| 仓库可查到的目录、命令、已有组件 | 自行调查并执行 |
| 已明确的设计、接口、技术栈和安装授权 | 沿用现有决定，不重复确认 |
| 可逆的普通实现选择，且不改变设计意图或业务语义 | 按现有模式决定，必要时简要记录假设 |
| 关键业务字段、权限、提交语义、需求范围或设计方向无法确定 | 准备具体差异与推荐处理，询问缺失决定；等待期间继续独立工作 |
| 用户明确要求设计/结构分阶段验收 | 完成该阶段可审阅产物后等待，未获确认不进入依赖阶段 |
| 工具、素材、账号、测试数据不可用 | 说明限制；可完成的独立部分继续，受影响结论保持未验证 |

确认是为解决具体决定，不是每个阶段都重新索取实施许可。没有未决项时按已授权任务连续推进。用户修改输入或阶段中断后，回读已变更文件，更新受影响映射和检查范围，不重新覆盖已有产物。

## 4. 调查、实现与回归

1. 读取最近作用域的AGENTS、工作区改动、路由入口、一个相近页面、共享组件和相关测试。定位请求客户端、主题/i18n入口及生成代码边界。
2. 建立变化清单：可复用组件、要扩展的接口、页面私有结构、必须保留的行为。新公共抽象需要稳定复用需求；含权限或业务状态的逻辑留在业务域。
3. 按选中来源完成设计解析或行为分析；涉及API时执行 [API流程](api-workflow.md)。没有设计变化的修复可以直接从复现进入相关测试。
4. 编码前核对适用项：来源可用、目标明确、未决阻塞已解决、组件与状态有落点、请求字段有依据、验证命令真实存在。关键材料缺失时不把推测写成已确认事实。
5. 新行为和缺陷按项目测试栈建立针对性失败用例，再实现和重构。涉及共享组件、缓存、路由或权限时扩大调用方回归；低影响视觉修改采用风险匹配的验证。
6. 按布局、交互、数据接入的依赖逐段完成可运行结果。将错误、空数据、权限和提交反馈与主流程一起实现，避免最后用假数据掩盖缺口。
7. 执行 [验收矩阵](acceptance-matrix.md)，失败修复后重跑相关检查；已通过且未受后续修改影响的检查无需反复执行。

能力组合以 [项目任务路由](../../project-workflow/references/task-routing.md) 为准。UI质量适用时用 web-design-guidelines；认证、输入、上传、敏感数据或新API涉及信任边界时用 security-review；接口契约用 api-design；React实现适用时用 vercel-react-best-practices。按当前宿主可用能力执行，不能把提到 Skill 名称当作已调用。

## 5. 命令和交付

命令从画像、package脚本、锁文件及CI配置确认，使用目标已有包管理器。缺少某项命令时报告事实，不执行虚构的 `test:e2e` 或 `type-check`。运行顺序为相关测试、适用静态/类型检查、构建及项目总门禁；随后完成真实页面验收。

只有规则、画像、Skill、校验配置等AI指引变化时，才额外执行指引校验。优先使用画像中已登记的实际命令，使用项目内 `node .codex/scripts/check-ai-guidance.mjs --root .`。只有实际采用外部资源的项目才从manifest定位外部来源。不得因为本文件提到校验就给普通页面任务新增门禁。

按 [验收证据模板](../../../../docs/AI_ACCEPTANCE_EVIDENCE.md) 交付用户可完成的结果、改动范围、实际命令、路由和操作、视觉差异、接口结果及未验证项。需要开发服务器的应用完成后保持可访问并给出URL；可直接打开的静态HTML给出文件入口。端口占用时使用其他可用端口。

构建成功、截图生成或HTTP 200各自只能证明相应检查。Browser不可用时给出逐区域自检和缺失原因；模拟环境与真实联调分别记录，不能静默回退为成功数据。
