# 前端任务共用执行契约

适用于截图、原型、HTML、Figma、API、文字需求及其组合。先按 [来源路由](source-routing.md) 选择材料，再应用本文件的任务规模和执行边界。纯文档、纯后端任务由 project-workflow 处理。

## 1. 建立可执行任务

先从用户目标判定四类任务之一，再独立记录影响模式和来源材料：

- `new-page`：新增路由、页面或完整页面级体验；
- `incremental`：修改已有页面/组件并保留未涉及行为；
- `bug-fix`：修复可复现缺陷；
- `refactor`：内部结构变化且外部契约等价。

影响模式可多选：`visual`、`behavior`、`data`、`structure`、`compatibility`。不要为了来源或影响模式新增任务类型。

从对话和仓库补齐下表，不要求用户重新填写已知信息：

| 字段 | 要确定的内容 | 主要依据 |
| --- | --- | --- |
| 目标与任务类型 | 用户最终完成什么；四类 taskType | 当前请求和复现步骤 |
| 影响模式 | visual/behavior/data/structure/compatibility | 变化清单与受影响调用方 |
| 代码与运行入口 | 路由、页面、组件、启动方式、测试 | 路由配置、邻近实现、package/CI |
| 输入材料 | 路径/URL、版本、节点、状态、视口/DPR | 已提供材料和源码 |
| 来源职责 | 每个来源负责视觉、行为、业务或工程哪一部分 | 来源内容与项目事实 |
| 保留行为 | 权限、导航、数据协议、样式与其他页面关系 | 代码、测试、业务契约 |
| 完成条件 | 可观察结果、适用检查、允许保留的未验证项 | 用户要求和画像 |
| 决策状态 | confirmed/derived/unverified/blocked | 证据和用户决定 |

关键结论：构建成功、截图生成、HTTP 200 或 mock 成功只能证明对应检查，不代表整个任务完成。

## 2. 按任务和影响选择产物

| 任务 | 必须调查 | 执行重点 |
| --- | --- | --- |
| `new-page` | 流程、布局、状态、组件、接口、支持端 | 先建立页面和状态边界，再实现主路径 |
| `incremental` | 变化区域、依赖方、原行为、回归范围 | 扩展现有模式，保护邻近区域 |
| `bug-fix` | 复现步骤、预期/实际、根因、相关测试 | 先复现，再最小修复，再重放和邻近回归 |
| `refactor` | 对外接口、调用者、状态生命周期、视觉基线 | 证明等价，不顺带重做视觉 |

按影响模式补充产物：

- `visual`：设计解析、来源视口截图、逐区域差异和资产清单；
- `behavior`：状态转换、操作路径和交互证据；
- `data`：UI 状态到请求状态映射、字段/权限/错误契约；
- `structure`：组件调用方、路由/构建影响和回归范围；
- `compatibility`：目标端、断点、主题、键盘、触摸、安全区域和短屏矩阵。

页面级设计产物默认 `docs/design/<页面>.md`，接口产物默认 `docs/api/<模块>.md`，对比材料默认 `docs/design/compare/<页面>/`。只创建实际需要的文件。

## 3. 来源职责与冲突消解

不要使用全局来源优先级，按事实领域和区域绑定来源：

- 工程事实：仓库代码、配置、测试和项目画像；
- 业务/数据事实：可信需求、API 契约和服务端行为；
- 视觉事实：用户明确选择的最新视觉版本，按区域和状态绑定；
- 行为事实：可交互原型或既有可运行行为；
- 生成代码：理解和实现参考，不覆盖项目事实。

组合规则：

- 截图 + 原型：原型负责流程，截图负责外观；
- 截图 + API：截图负责视觉，API负责字段、请求和状态；
- 原型 + API：原型负责演示流程，API负责真实提交语义；
- HTML + 截图：HTML负责保留行为，截图负责指定视觉变化；
- Figma + 截图：按版本、区域和状态绑定，冲突记录后再实现。

冲突必须记录区域/字段、来源A/B、影响、推荐处理、依据和是否需要用户确认。无法消解的高影响冲突不得被静默覆盖。

## 4. 调查、实现与回归

1. 读取最近作用域的 AGENTS、工作区改动、路由入口、相近页面、共享组件、请求客户端、主题/i18n 入口和相关测试。
2. 建立变化清单、影响模式、来源责任、资产清单、组件决策和状态矩阵。
3. 编码前核对来源可用、目标路由、目标端、视觉基准、字段来源、权限语义和未决阻塞。
4. 新行为和缺陷按项目测试栈建立针对性失败用例，再实现和重构；低风险视觉改动采用风险匹配的视觉验证。
5. 按布局、交互、数据依赖逐段完成可运行结果；错误、空、权限和提交反馈与主流程一起实现。
6. 执行验收矩阵，失败修复后重跑相关检查；后续修改影响的证据必须失效并重验。

## 5. 端目标和完成状态

显式区分：

- `sourceViewport`：来源截图或设计实际覆盖的视口；
- `confirmedTargets`：项目画像或用户明确确认的目标端；
- `derivedTargets`：按项目规则推导的端；
- `unverifiedTargets`：尚无证据的端。

不要因一张桌面截图声称移动端已完成。最终至少分别报告：

```text
visual: passed / failed / unverified
behavior: passed / failed / unverified
data: passed / failed / unverified
engineering: passed / failed / unverified
```

## 6. 失败处理和交付

每个失败记录触发条件、预期、实际、来源或代码定位、影响及后续动作。`bug-fix` 无法复现时标记未确认；`refactor` 无法证明外部等价时标记未完成或降级为待确认。

证据至少包含任务/来源版本、实际路由、环境、命令及退出码、操作步骤、截图或脱敏请求记录、偏差和未验证项。没有 Browser、接口或账号时，交付已验证部分及继续条件。
