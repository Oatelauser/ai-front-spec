# 原型转页面与用户流程

适用：线框原型、原型图、交互演示、原型工具导出HTML。目标是从演示中提取可实现的流程与页面；已有业务HTML迁移使用 [HTML流程](html-workflow.md)，选定视觉图的忠实实现使用 [截图流程](screenshot-workflow.md)。共用规则见 [执行契约](common-workflow.md)。

读取 [项目画像](../../../../docs/PROJECT_PROFILE.md) 的路由、状态、组件及支持端约定，复用 [组件目录](../../../../docs/rules/AI_COMPONENT_CATALOG.md)。原型通常表达结构与交互，不自动成为正式样式或后端行为的权威来源。

## 1. 输入与可访问范围

记录原型入口、版本、页面清单、目标路由、角色、交互说明、导出资源、接口资料以及需要保留的现有流程。先查材料，再询问缺失的关键决定。

| 材料 | 查看方式 | 需要补充的证据 |
| --- | --- | --- |
| 静态线框/原型图 | 打开每个相关页面和状态 | 跳转、返回、校验和提交说明 |
| 可交互原型链接 | 在实际可用浏览器中操作任务相关路径 | 操作起点、动作、结果及不可访问节点 |
| 导出HTML | 检查入口、页面文件、资源和脚本依赖，按支持方式本地查看 | 缺失资源、链接目标、运行限制 |

不要为查看原型执行未知安装器。只有静态图时不能声称实际点击过；链接失效或演示状态不可达时标记未观察，而不是自动补成已确认行为。导出代码以理解原型为目的，是否迁移代码由任务要求决定。

## 2. 建立流程和状态模型

先走一遍主路径，再看返回、取消和失败路径。在目标设计文档中记录页面/路由关系与下面的状态转换表；局部改动只更新受影响步骤。

| 当前页面/状态 | 触发动作 | 前置条件/校验 | 后续页面/状态 | 数据保留与副作用 | 来源/未决项 |
| --- | --- | --- | --- | --- | --- |
| 示例：基本信息 | 下一步 | 必填字段通过 | 选择处理人 | 保留本步输入；是否存服务端待契约确定 | 对应原型页面及说明 |
| 示例：确认页 | 返回修改 | 无新增条件 | 上一步 | 保留已输入值，不能重复提交 | 对应返回连线 |

逐项确认适用问题：

- 页面是独立路由、页内步骤、弹层还是抽屉；直接访问、刷新及浏览器返回如何表现。
- 表单的字段依赖、必填规则、校验时机、错误位置和禁止继续条件。
- 返回上一步、关闭弹层、取消和离开页面时输入保留在哪里；敏感数据是否允许持久化。
- 提交动作的触发点、进行中状态、成功去向、失败重试；演示跳转不等于请求已成功。
- 列表选择、批量操作、筛选和详情之间的数据关系，以及空列表、未选择、无权限情况。
- 角色和权限是否有可信契约。隐藏按钮只能是显示策略，不能代替服务端鉴权。

简单交互使用已有组件状态；复杂流程先明确合法状态和转换，再复用项目已有状态管理。不要仅凭页面多就新建全局store或状态机框架。

## 3. 视觉方向、组件与接口

将信息结构映射到现有壳层、表单、步骤导航、列表、详情、反馈和弹层组件，记录“复用、扩展、业务域、页面私有”的决定。按职责划分组件，页面负责流程编排，公共组件不直接请求业务接口。

视觉处理按材料地位选择：已有系统沿用现有设计；明确指定的截图按截图流程；没有定稿且任务要求设计时，按项目路由使用适用的设计能力提出方向。用户已经选定的布局和样式直接沿用，不因为输入叫“原型”就全部重做。

设计产物包含结构树、组件接口、状态转换、Token候选、图标与文案、支持端变化。原型占位文案需要转换为已确认业务文案，语言和主题服从画像。

涉及服务端动作时执行 [API流程](api-workflow.md)，把每个动作对应到请求及其状态。接口缺失时输出明确标为“草案，待后端确认”的契约问题，不把演示脚本中的假数据当作真实服务。用户已授权模拟原型时可先实现本地状态，交付时说明数据来源。

## 4. 何时确认与进入编码

主要流程、成功结果、关键校验、取消/返回语义和适用接口已明确后即可编码。未确定的视觉方向、会丢失输入的离开策略、权限或提交副作用先准备具体选项并确认；现有业务规则能回答的内容自行读取。

用户要求先审阅流程或结构时，交付路由/状态表与组件计划后等待；否则沿用已有决定，按共用契约连续推进。未确认部分不妨碍完成独立组件或已明确步骤。

## 5. 从主路径实施到异常路径

1. 按目标路由接入现有壳层，先让流程起点和导航可访问。允许在一个有效路由内实现多个页内步骤；只有独立访问、刷新恢复等已确认需求需要时才拆分路由，不能交付脱离目标应用入口的孤立演示。
2. 在负责该流程的业务模块管理草稿和选择状态，区分临时输入、已保存服务端数据和派生显示值。
3. 完成最短主路径，再补返回、取消、校验和失败路径；同一个提交动作只保留一个明确入口和进行中反馈。
4. 接入请求、统一错误和权限处理。成功跳转依赖真实结果或明确模拟结果，不能只定时跳到成功页。
5. 为状态转换和关键规则增加针对性测试；跨步骤、路由和请求的组合使用项目已有集成/E2E方式验证。

## 6. 验收与证据

按 [验收矩阵](acceptance-matrix.md) 使用实际质量命令并操作以下适用路径：

| 路径 | 验收重点 |
| --- | --- |
| 从入口完成主流程 | 每个步骤可达、反馈正确、结果可查看 |
| 无效输入后修正 | 错误定位清楚，修正后能够继续 |
| 上一步、关闭、重新进入 | 输入和选择按已确认策略保留或清理 |
| 提交失败后重试 | 原输入可恢复，不重复创建业务结果 |
| 直接打开中间路由与刷新 | 前置状态不足时合理引导，无空白或假成功 |
| 键盘与窄屏 | 步骤、弹层、表单和主要操作均可达，无内容遮挡 |
| 不同角色或数据状态 | 权限、空态、加载、错误与主路径一致 |

交付 [验收记录](../../../../docs/rules/AI_ACCEPTANCE_EVIDENCE.md)，附原型版本、覆盖页面/步骤、实际动作、实现与演示的有意差异、接口验证范围和未观察状态。截图只证明状态外观，流程成功需要真实操作证据。
