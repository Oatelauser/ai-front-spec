# 从文字需求到页面与流程

适用：没有定稿设计的新页面、业务流程或重新设计任务。已有设计源时由对应 [来源流程](source-routing.md) 负责视觉；对明确的现有页面缺陷，先按 [共用契约](common-workflow.md) 复现与修复，不因为用户用文字描述就重新设计页面。

先读取 [项目画像](../../../../docs/PROJECT_PROFILE.md)、[任务合同](../../../../docs/AI_TASK_CONTRACT.md) 和 [组件目录](../../../../docs/AI_COMPONENT_CATALOG.md)。目标是把用户需求转换成可验证的结果，技术栈和既有业务事实不能被设计偏好覆盖。

## 1. 从需求提取任务合同

记录用户目标、使用角色、使用场景、目标路由或代码范围、已有系统、接口资料和保留约束。从仓库优先回答组件、权限入口、数据来源和测试命令等可调查问题。

| 维度 | 要回答的问题 | 产出 |
| --- | --- | --- |
| 用户目标 | 谁在什么场景完成什么事情 | 一句话目标和主流程 |
| 业务范围 | 本次明确要求哪些动作，哪些只是可能的扩展 | 本次范围与未决项 |
| 数据 | 展示/编辑哪些实体和字段，来源在哪里 | 数据需求与契约引用 |
| 交互 | 入口、主要动作、完成反馈、返回和失败恢复 | 流程与状态清单 |
| 权限 | 谁能看、谁能操作，依据哪个可信来源 | 角色/动作边界 |
| 体验 | 现有设计系统、目标终端、内容密度、主题和语言 | 页面与适配约束 |
| 验收 | 怎样观察到用户目标完成 | 可执行用例 |

区分明确需求、仓库已确认事实、合理实现选择和待决定业务项。例如“通知中心”不自动包含消息推送、订阅偏好和管理后台；“导出”也不能自行决定文件格式、字段范围和权限。

## 2. 将目标拆成可观察用例

用“前置条件、用户动作、预期结果”描述主流程，再补与本次功能有关的边界。若用户只要求计划或原型，完成条件限定在该范围。

| 示例：通知中心 | 前置条件 | 用户动作 | 预期结果 |
| --- | --- | --- | --- |
| 查看未读 | 存在可见通知 | 切换未读筛选 | 只显示当前用户可见的未读通知 |
| 打开详情 | 有可访问的通知 | 打开一条通知 | 展示对应内容；是否自动标已读依据业务规则 |
| 标记已读 | 契约支持该动作 | 点击标记 | 成功后计数与列表一致，失败有恢复入口 |

示例用于说明拆解方式，不代表当前任务已批准这些字段或动作。确认不了的“是否自动标已读”属于业务决定；列表间距、复用现有抽屉等普通选择可自行完成。

为适用用例补充首次加载、合法空结果、失败、无权限、禁用、成功和重试。表单补充校验和取消，列表补充筛选/分页与返回，复杂流程补充中断和重新进入。不要为纯展示任务制造无关服务端状态。

## 3. 信息结构与视觉方向

1. 先找到相近页面和可复用壳层、导航、表单、列表、详情、反馈组件，确定本次入口和用户完成任务的最短路径。
2. 按使用频率和决策顺序组织字段、主次操作、筛选、详情与反馈。运营工具优先可扫描的信息和稳定操作位置；其他领域结合实际用户目标选择表达。
3. 已有设计系统时沿用其布局、Token、图标、字体、主题和语言规则。用户指定视觉方向时直接应用，不再提出无关替代方案。
4. 新视觉确需探索时，按项目任务路由使用适用的Product Design或设计方向能力；遵循被加载Skill的输入和工具要求。通常提供一个有依据的推荐方案，存在实质不同取舍时再比较候选。
5. 为本次范围记录页面布局、组件职责、状态、文案/图标/资产、支持端适配和关键交互。需要展示方案时使用当前可用的可视化方式，不能声称已生成未实际产出的设计图。

新建或更新 `docs/design/<页面>.md`，路径以目标约定为准。文档用于保存设计决定和实现依据，不把长篇功能说明、内部实现细节或操作教学塞进产品页面。

原有视觉适用的局部需求只更新相应区域。没有明确需求时不新增主题、语言、路由体系、组件库或大型状态管理设施。

## 4. 数据契约与实施范围

已有接口资料时按 [API流程](api-workflow.md) 核对字段、动作、权限和错误语义。文档缺失时先列出影响实现的具体缺口；可起草契约并标明“待后端确认”，不能把建议写成已存在API。

| 当前条件 | 可以完成的范围 | 交付边界 |
| --- | --- | --- |
| 有项目、设计系统和可用契约 | 页面、交互、数据接入及实际验收 | 按真实环境证据报告 |
| 有项目但接口未提供，已授权本地原型 | 使用项目约定的明确模拟数据实现交互 | 保留真实接入未验证项 |
| 仅要求方案或需求梳理 | 合同、用例、布局/组件计划、数据缺口 | 不自动写业务代码 |
| 已授权基于本模板创建应用，尚无业务工程 | 在当前根目录补规则，按已决定栈创建工程，保留模板文件，再更新实际画像与实现页面 | 规则初始化与业务可运行分别验收 |

关键业务含义、权限、提交副作用或新设计方向确实未确定时，先给出具体推荐和影响，等待相应决定。已授权代理自主决定的普通产品/工程细节继续推进，不反复要求用户批准同一方向。

## 5. 编码前检查与分步交付

进入编码前，适用项应具备明确落点：目标路由、范围与用例、复用组件、主要状态、视觉依据、数据边界和真实质量命令。高影响未知项未解决时，完成独立的已明确部分，说明暂时无法交付的结果。

1. 先接通一个完整主流程，使入口、主要动作、结果反馈可实际操作；必要的错误和权限处理与主流程同步实现。
2. 将变化的业务规则和状态转换写成可测试逻辑，复用现有测试栈实施针对性验证。页面私有布局不为抽象而抽象。
3. 逐步接入接口与缓存，核对表单、筛选、详情和反馈的一致性；模拟实现与真实接入保持可辨识，不设置静默成功回退。
4. 完成支持端布局、键盘和焦点、适用语言/主题及极端数据检查。实现阶段使用适用的frontend-design和项目框架规则。
5. 对照原任务范围检查功能，避免实现过程中自行增加导出、管理功能或其他新业务模块。需求变化时更新合同和受影响用例。

## 6. 以用户用例验收

运行项目相关测试、静态/类型检查、构建及总门禁，再按 [验收矩阵](acceptance-matrix.md) 从入口实际完成每条必需用例。核对成功结果、失败恢复、权限、刷新以及桌面/平板/移动的适用行为。

| 交付项 | 应能回答 |
| --- | --- |
| 功能结果 | 用户现在能完成哪些已要求的操作 |
| 设计与范围 | 沿用了什么，新增/调整什么，决定依据在哪里 |
| 数据 | 哪些来自真实接口，哪些仅模拟，契约还有哪些未决项 |
| 验证 | 实际命令、视口、路由、动作和结果是什么 |
| 剩余项 | 哪些失败或未验证，原因及继续条件是什么 |

通过 [验收记录](../../../../docs/AI_ACCEPTANCE_EVIDENCE.md) 保存证据，提供实际可访问的应用入口。无接口或Browser时交付已验证部分，不能用“页面已生成”替代用户目标已完成。
